# Aquarium Civ — Prototype & A/B Test Plan (draft v0.1, 2026-10-28)

Status: **approved 2026-10-28.** All four concept variants ([game-definition.md](game-definition.md) §12) are prototyped. P0 started.

Goal: find out what's fun with small throwaway Unity prototypes. Each one tests **one hypothesis**, takes 1–3 days
of agent work, and is ordered so the **riskiest assumption comes first: is caring for the tank fun, not a chore?**

## 2. Shared foundations (P0, ~3 days)

### Layout and isolation
```
Assets/Prototypes/
  _Shared/
    Runtime/          AquariumCiv.Prototypes.Shared.asmdef  (pure C# sim + MonoBehaviour views)
    Tests/            EditMode tests for the sim core
    Prefabs/, Materials/, Shaders/ (grime shader)
  P1_GlassMess/       scene + prototype-only scripts (own asmdef, refs Shared)
  P2_ReturnToMess/
  ...
Assets/Editor/Agent/
  DioramaBuilder.cs   (refactored out of LookTestBuilder: builds the KayKit glass diorama into any scene)
  PrototypeSceneBuilder.cs (one menu item per prototype scene)
```
- Every prototype is a separate scene under `Assets/Prototypes/<Name>/`. Prototype code never references
  another prototype, only `_Shared`. Deleting a prototype folder must not break anything.
- Scenes are generated by editor builders (like `LookTestBuilder`), not hand-edited, so they're cheap to rebuild.
- Reuses the look-test diorama (KayKit hex village in glass, portrait camera, tilt-shift post-processing).

### Components
| Component | What it does |
|---|---|
| **SimClock** | Two clocks: **civ time** (compressed, default 1 real h ≈ 1 game year) and **care time** (real hours). A debug multiplier scales both. Default and test speed: **1 real hour = 1 game year** (notables age at half speed). Debug presets for development only: ×60 (1 min = 1 y), ×600, *Pause*. Stores last-seen UTC for offline catch-up. |
| **Away button** | "+1 h / +8 h / +48 h away": runs exactly the same catch-up path as a real app resume. |
| **Sim core** | Pure C#, deterministic from a seed, coarse step = 1 game month. State: population, food, materials, mood, output rate, mess (grime 0–1, trash count, overgrowth 0–1), buildings, notables (name, age, trait, parents, event refs). Covered by EditMode tests (determinism, catch-up equals live stepping, mess cap). |
| **Event generator** | Templates filled from sim state ("Narrative Legos"), each with a salience score. Used from P3 on; P0 ships the plumbing plus about 10 templates. |
| **Views** | DioramaView (buildings appear as the sim grows), CrowdView (KayKit characters wandering between buildings on waypoints; no NavMesh needed yet), MessView (grime shader with a paintable mask, trash props, vine props). |
| **Camera** | Orbit-the-pot: one-finger rotate, pinch zoom, tap to focus. New Input System (EnhancedTouch). |
| **Event log** | JSON Lines in `Application.persistentDataPath/logs/`. See §3. |
| **Survey panel** | 5 questions at the end of a session ("Done for now" button, or prompted after lab sessions). |
| **Debug panel** | Time slider, away buttons, variant switch, log export. Hidden behind a 3-finger tap; only in dev builds. |
| **Variant assigner** | Picks the A/B variant per session from a schedule (lab: fixed order per tester; diary: alternate days) and records it in every log line. |
| **Tester identity** | Nickname on first launch plus a random GUID. No accounts, no personal data. |
| **Log export** | "Copy summary" button puts a compact per-session JSON summary on the clipboard for testers to paste into a chat. The raw JSONL stays on the device. (Optional later: NativeShare, MIT, to share the full file.) |
| **iOS build** | Testers are on iPhone → **TestFlight**. No Mac, so builds go through CI: GameCI exports the Xcode project on Linux, then fastlane signs and uploads on a `macos-26` runner (fallback: Unity Build Automation's 100 free Mac min/month). See [05-github-cicd.md](../research/05-github-cicd.md). Friends join as internal testers (added as App Store Connect users, no Beta Review) or external testers (one Beta App Review per build). |

### P0 done when

- "+8 h away" produces a grown village, accumulated mess, and a log line.
- EditMode tests pass.

## 3. What we log (all prototypes)

One JSON object per line: `{ "t": UTC ISO, "tester", "session", "proto", "variant", "ev", "data": {...} }`

| Event | Data |
|---|---|
| `session_start` | build, real hours away, game years elapsed, mess level on open |
| `session_end` | duration (s), reason (background / done button) |
| `tap` | screen position, hit category (glass, trash, vine, building, citizen, notable, UI) |
| `look` | sampled every 0.5 s, aggregated per session: seconds spent looking at each category (raycast from screen center + focus target) and seconds zoomed in vs out |
| `camera` | rotations, zoom changes (counts, not raw stream) |
| `clean` | kind (glass / trash / vine / weather), amount cleaned, gesture, dirt level before, **voluntary** flag (dirt < 10 % before) |
| `chronicle_view` | card id, dwell seconds, fly-to tapped |
| `notable` | tap / pin / unpin, notable id |
| `nudge` | kind, target, game-time effect seen (later) |
| `history` | open, dwell seconds, scrub distance, page turns, screenshot taps |
| `survey` | the 5 answers |
| `debug` | time-scale changes, away-button presses (so debug sessions can be filtered out) |

The session summary (for the clipboard) holds: duration, taps per category, look-time per category, cleans
(total / voluntary), chronicle cards read, nudges, history time, and survey answers.

## 4. Test protocol (shared)

**Who:** the user plus 3–5 friends on iPhone (TestFlight). With so few testers, every A/B is **within-subject**: each tester
plays both variants, with the order counterbalanced (half A→B, half B→A). Results are directional, not
statistical. We look for agreement (e.g. "5 of 6 preferred B") plus logged behavior that backs it up.

**Two kinds of tests**
- **Lab (15–20 min, debug time scale):** a short brief ("this is a tiny world in a jar; look after it"), then
  ~7 min variant A, survey, ~7 min variant B, survey, then one question: "Which did you prefer, and why?"
- **Diary (3–4 real days, design time scale, no debug panel):** the app sits on the phone like a real game.
  The variant alternates by day. Survey on "Done for now", at most once per day. No push notifications
  during tests (we're measuring unprompted returns).

**The 5-question post-session survey**

| # | Question | Format |
|---|---|---|
| 1 | That session felt… | 1 = like a chore … 5 = relaxing / fun |
| 2 | How much do you want to check on it again later? | 1–5 |
| 3 | Tell me one thing that happened or that you noticed in your tank. | free text (doubles as a **recall** measure) |
| 4 | *Prototype-specific* (see each prototype) | 1–5 |
| 5 | Did anything feel like work, confusing, or guilt-inducing? | free text |

**The user is the final judge of look and feel.** Tester data informs; it doesn't overrule.

## 5. Prototypes

### P1 Glass & Mess (care gesture) · 2 days · lab
- **Hypothesis H1:** cleaning the tank is satisfying in itself; people do it even when it's barely needed.
- **A/B (one variable: gesture):** **A** drag-to-wipe the glass (finger smears and clears the grime mask; trash and
  vines are flicked) vs **B** tap-to-clean (tap a smudge, trash or vine and it pops clean). Same mess, same juice budget.
- **In scope:** diorama, ambient crowd (no economy), grime shader with paintable mask, trash/vine props that regrow
  on the slider, juice (sound, particles, people cheering and waving), log + survey.
- **Out of scope:** economy, chronicle, notables, nudges.
- **Survey Q4:** "Cleaning felt satisfying" (1–5).
- **Metrics:** time to full clean, share of mess cleaned, **voluntary cleans** (dirt < 10 %), wipe strokes / taps per
  clean, look-time on the world vs the glass.
- **Fun if:** median Q1 ≥ 4 and Q4 ≥ 4 in at least one variant, **and** ≥ half of testers clean voluntarily.
  The variant that wins Q4 + preference is the gesture.
- **Not fun if:** Q1 ≤ 3 in both variants, or testers stop cleaning once the glass is "good enough" → flag
  Gate 1 risk early and add a juice pass before P2.

### P2 Return to Mess (neglect over real time) · 3 days · lab + 4-day diary
- **Hypothesis H2:** opening the app to find mess is a pull, not guilt; a slight output drop makes care matter
  without making it a chore.
- **A/B (one variable: consequence):** **A** mess is cosmetic only vs **B** mess + output drop (linear up to −25 %
  at the 48 h cap, shown in the ledger and as grumpier people). Both cap at 48 h.
- **In scope:** P1's winning gesture, minimal economy (population grows, huts appear), real offline catch-up,
  away button (lab), real time (diary), welcome-back wave.
- **Out of scope:** chronicle cards (just a one-line "+3 people, 1 new hut").
- **Survey Q4:** "I felt bad or guilty when I opened it" (1–5, lower is better).
- **Metrics:** unprompted opens per day, time from open to first clean, share of sessions with any cleaning,
  session length, D2/D4 return, guilt score.
- **Fun if:** B's opens/day ≥ A's **and** median guilt ≤ 2.5 → keep the output drop. If B raises cleaning but
  guilt > 2.5 → lower the cap (−10 %) or drop it. If both variants have opens/day < 1.5 by day 3 → the care loop
  doesn't pull → Gate 1 discussion.
- **Also tunes:** grime speed (how many hours until "noticeably dirty"), the 48 h cap.

### Gate 1: care pillar
Decide with the user: **Go** (care is a pillar; lock gesture + consequence) / **Reshape** (more juice, less mess,
different kinds) / **Fall back** to Variant B (care reduced to glass-only "care = clarity").

### P3 While You Were Away (return moment) · 3 days · lab + 4-day diary
- **Hypothesis H3:** a curated chronicle with named notables makes the return the highlight, and players remember
  their civ's story.
- **A/B (one variable: return presentation):** **A** 3–7 chronicle cards ranked by salience, with notable portraits
  (KayKit character + name + trait) and fly-to camera vs **B** plain return (you see the changed diorama plus a
  stats line; notables still exist and can be tapped in the world).
- **In scope:** event generator with ~30 templates (births, deaths of notables, firsts, buildings, weather, funny
  incidents), 5–12 notables with lineages (aging at half speed), tap a citizen → card, pin a favorite.
- **Survey Q4:** "I care about specific people in my tank" (1–5). Q3 recall is the key measure here.
- **Metrics:** cards read, dwell per card, fly-to taps, notable taps and pins, **recall** (Q3 mentions a specific
  person or event), session length.
- **Fun if:** in A, ≥ ⅔ of testers recall a specific named person or event, and A is preferred by most.
- **Also confirms Q3:** with notables at half speed (~5 real days of life), do testers still feel they die too soon?

### P4 Book of Ages (history display) · 3 days · lab + diary on the P3 build
- **Hypothesis H4:** being able to browse the civ's history is a reason to linger and share (the WorldBox itch).
- **A/B (one variable: history view):** **A** time-lapse scrubber (drag a timeline to replay the box growing, with
  event pins you can tap) vs **B** illustrated book (era chapters, notable portraits, family tree, key events).
- **In scope:** yearly snapshots recorded by the sim (compact: building list, population, notables), the two
  views, a screenshot button. Runs on top of the P3 sim, seeded with ~100 game years of pre-generated history so
  the lab test has something to browse.
- **Survey Q4:** "I'd show this to a friend" (1–5).
- **Metrics:** history opens (unprompted in the diary), dwell, scrub distance / pages, screenshot taps.
- **Fun if:** ≥ half of testers open history unprompted during the diary, and the winning view scores Q4 ≥ 4.

### Gate 2: history pillar + time compression
Lock the return presentation, the history view and the time compression.

### P5 Keeper's Nudge (control) · 3 days · lab + 3-day diary
- **Hypothesis H5:** indirect nudges make players feel they shaped the history, without micromanagement or helplessness.
- **A/B (one variable: nudge form):** **A** omens (place a shrine or totem → the civ leans toward farming, craft or
  faith) vs **B** environment shaping (rain, plant a grove, divert the stream; the people adapt). Both are credited
  in the chronicle ("After the Keeper's rain…").
- **In scope:** 3 nudges per variant, sim response within ~1–3 game years (~1–3 real hours, faster in lab), chronicle credit.
- **Survey Q4:** "I felt I shaped what happened" (1–5), plus a free-text follow-up on control ("too much / too little").
- **Metrics:** nudges per check-in, time from nudge to first visible effect, whether players look for the effect
  (look-time on the nudged area).
- **Fun if:** Q4 ≥ 4 and a nudge is used in ≥ 60 % of check-ins. Variant B's result also informs the
  deep-session terraform/decorate layer.

### P6 Eras & Shelf (progression) · 2–3 days · lab
- **Hypothesis H6:** an era transition witnessed live is a payoff worth waiting for; one of the two growth forms
  motivates clearly more.
- **A/B (one variable: growth form):** **A** the box grows (lid opens, an annex box attaches, the world extends) vs
  **B** a new box on the shelf (the old one keeps living as a museum, relics carry over).
- **In scope:** a staged Camp → Hamlet → Village transition (KayKit only), a live "era threshold" moment, both
  growth forms as short scripted sequences, a shelf view with 2 boxes.
- **Survey Q4:** "I want to see what comes next" (1–5).
- **Metrics:** preference, Q4, time spent in the transition, and in B, time spent revisiting the old box.
- **Fun if:** the transition scores Q1 ≥ 4 for most testers, and one growth form wins preference clearly
  (≥ ⅔). A tie means both stay (the current design).

### Gate 3: control + progression
Lock the nudge form and the progression shape, then write the **vertical-slice plan** (one box, eras 1–3, final art
direction, real save/catch-up architecture).

## 6. Not prototyped (decided or deferred)
- **Named vs anonymous citizens:** decided (crowd + notables). Revisit only if P3 shows weak attachment.
- **Disease:** out of scope for now.
- **Monetization:** a hypothesis; validated later with real players, not prototypes.
- **Notifications, widgets, cloud save:** vertical-slice concerns.

## 7. Working rules for prototype builds
- Follow `CLAUDE.md`: Unity status check before edits, `--timeout 60` on short calls, background + 1-minute check-ins
  for long ones, recompile + console check after every C# change, screenshots for visual changes.
- Commit before each prototype scene is generated, and tag each tested build (`proto/P1-v1`, ...).
- Each prototype ends with a short results note in `docs/design/results/Pn.md` (metrics, survey quotes,
  decision), and the decision goes into `docs/decisions.md`.
